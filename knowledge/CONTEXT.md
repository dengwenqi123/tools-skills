# CONTEXT

本仓库的领域词汇表。**只定义概念，不写实现细节** —— 实现约定在 `AGENTS.md`，
决策记录在 `docs/adr/`。

当前收录范围：crashlog 模块的 crash 资源调度与提单链路（`send_init_crash_to_queue`
所在的 B 路径），以及承载解析任务的**解析机与 agent 实例**拓扑。其余链路的术语尚未
收录，遇到时再补，不要凭猜测填写。

## Crash 资源与状态

### crash 资源 (crash resource)
一次设备崩溃上报的**整体**，对应 `vela_crash_resource` 一行。一个资源可以包含
多个核的日志与分析产物。资源是调度、提单、去重的基本单位。

### 核 (core)
崩溃设备上的一个处理器核心。已出现的取值：`ap`、`cp`、`sensor`（亦作 `sen`）、
`audio`、`tee`、`android`。同一次崩溃通常会同时产出多个核的日志。

### analysis_status（资源级状态）
`vela_crash_resource.analysis_status`，描述**资源**在调度链路中的位置。五个取值：

| 状态 | 含义 |
|------|------|
| `init` | 等待调度处理。可提单场景的资源落库后的初始状态；也是各类"数据未就位、下一轮重试"的回退目标。 |
| `processing` | 已被某个调度进程接管、正在处理。**秒级中间态**，不应长期停留。 |
| `published` | 已发往消息队列，交由下游做符号化与相似度匹配。终态。 |
| `finished` | 已完成，但走的是提异常单而非发消息队列（无可用 backtrace 等场景）。终态。 |
| `error` | 处理失败且判定为不可自动恢复，停止重试。 |

### task_status（任务级状态）
`vela_crash_analyze_task.task_status`，描述**单个核的单个分析任务**的进度。取值
`init` / `analyzing` / `finished` / `error` / `timeout`。

> **`analyzing` 属于任务，不属于资源。** 资源的"正在处理"叫 `processing`。这两个
> 词不可互换 —— 混用会导致误判卡死资源的兜底逻辑。

### 卡死资源 (stale resource)
长时间停留在 `processing` 的资源。正常 `processing` 是秒级中间态，长期停留意味着
接管它的调度进程中途死亡、或某条代码路径漏写终态。

## 提单路径

### A 路径
崩溃日志落地时**同步**触发的提单路径。直接调 JIRA API 出单，不发消息队列。完成后
把资源置为 `finished`。

### B 路径
定时调度**异步**触发的提单路径。捞 `init` 资源，发消息队列，由下游回调完成提单。
成功后把资源置为 `published`。

> 两条路径靠 `analysis_status` 互斥：B 路径只查 `init`，所以 A 路径先置 `finished`
> 就能阻止 B 路径重复处理同一资源。

### 可提单场景
B 路径愿意接管的资源类别，由资源的 `remark` 判定。目前两类：**VTF Monkey crash**
与 **UFI 离线补提**。

### VTF Monkey crash
VTF 测试框架 Monkey 压测产生的崩溃。B 路径最初唯一接管的场景。

### UFI 离线补提
UFI 渠道离线回捞的崩溃上报。特征是**没有 coredump**，因此 A 路径出不了 crash 单，
只能靠 B 路径接管。

## 就绪判定

### 就绪 (readiness)
资源的各核分析产物是否**已经齐备到可以安全消费**。未就绪就消费，会拿到"半成品"
数据，选中错误的核，产出与真实崩溃错位的结论。

### 必检 diag_report
判定就绪时，**结构上应当产出诊断报告的核**的集合。有些核结构上根本不产出诊断报告
（如 `tee`），把它们计入必检会让就绪判定永远等不到、退化成无脑死等超时兜底。

### 推迟 (deferred)
本轮判定为未就绪、因此**不予接管**的资源。推迟不是失败：资源保持 `init`，下一轮
重新判定。

### 兜底超时 (readiness timeout)
就绪判定的止损窗口。资源创建时间超过该窗口仍未就绪，直接放行，防止某个永远跑不完
的任务把资源永久堵住。

## 崩溃归因

### backtrace
崩溃线程的调用栈。这条链路上以"每帧一行、`路径:行号 函数名`"的列表形式流转。

### 首崩溃核 (first crash core)
多核崩溃中**最先崩溃**的那个核 —— 真正的故障源。

### 受害核 (victim core)
被首崩溃核连带拖崩的核。它的调用栈看起来也是崩溃，但归因到它会指错责任人。启发式
挑核容易挑中受害核，所以需要专门的首崩溃核判定。

### 核对齐 (core alignment)
发往下游的 backtrace 所属核，与后续提单所依据的核**是否是同一个核**。不对齐会
产生"消息队列里是 CP 核、JIRA 单里是 AP 核"的错位。

### crash 定界 (crash triage to team)
判断一个 crash 问题**属于哪个领域团队**。输出是团队，不是人，也不是垂域。只对
**新问题**做；去重命中的沿用老单归属。
_避免_：单说"定界"——circle 全闭环的"每日异常定界"是另一件事。

### 重复问题 (duplicate)
与历史问题是**同一个 bug**，去重后合入同一张单，不新建。

### 相似问题 (similar)
与历史问题**不是同一个 bug，但崩在相近的代码区域**。不合单，只作为 crash 定界的
证据（看它最终归属哪个团队）。

> 重复与相似共用同一批历史候选，按相近程度区分；"相似"永远不触发合单。

### resolver
崩溃归属人的快照，随消息发往下游供检索与入库使用。**它不反向决定实际指派** ——
指派由 owner-config 统一收口。

## 提单产物

### 工具异常单
针对**分析工具链自身失败**（符号化失败、coredump 与 elf 不匹配等）开的 JIRA 单，
交工具负责人。

### crash 单
针对**业务崩溃本身**开的 JIRA 单，交崩溃代码的负责人。

> 同一个资源可能**两种单都出**：工具没能给出可用栈（出工具异常单），但确实发生了
> 崩溃、需要人工分析（再出 crash 单）。

### coredump_incomplete
一个提单原因标记，表示 coredump 不完整/不可用因而无法产出可用 backtrace。

## 解析机与 agent 实例

### 解析机 (parse host)
一台承载崩溃解析的物理机，运维登录的对象。命名形如 `mina03`、`vela16`。解析机
**不直接执行解析**，它只是若干 agent 实例的宿主。

### agent 实例 (agent instance)
一个独立运行的解析 agent 进程单元，从服务端轮询领取分析任务并执行。一台解析机
同时运行**多个**实例，实例数按该机器的算力单独设定，机器之间不必相同。

### node_name
一个 agent 实例的唯一标识，形如 `<解析机>_<序号>`（如 `mina03_1`、`vela16_12`）。

> **`node_name` 标识的是实例，不是机器。** 口语里的"节点"两种含义都在用，这是本
> 系统最容易错位的一处词汇：`vela_crash_analyze_task.node_name` 存的是**实例名**，
> 因此"这台机器处理了多少任务"必须按 `<解析机>_` 前缀聚合，而不是按等值匹配。
> 历史数据中同时存在无后缀的实例名（如 `mina03`），是早期一机一实例时期的遗留。

### 实例序号 (instance ordinal)
`node_name` 后缀的序号，在**同一台解析机内**从 1 连续编号。序号只需机内唯一，
跨机器可以重复。序号的书写形式一经确定不可更改，见 `docs/adr/0003-*`。

## 提单回归（crashlog A 路径 + autotest）

### 提单动作 (ticket action)
一次提单流程对一个输入给出的结论，三选一：

| 动作 | 含义 |
|------|------|
| 新建 | 没有可复用的未关闭单，开一张新 JIRA 单。 |
| 复用 | 查重命中一张未关闭单（autotest 沿 duplicate 链取根单），只追加/合并 comment，必要时 reopen，不新建。口语里的 "deep" 指的就是它。 |
| 跳过 | 按业务规则不该提单（debug remark、超龄、开关关闭等）。跳过是**正确结论**，不是失败。 |

> **"提不了单" ≠ 跳过。** 提不了单是期望新建/复用、实际什么都没发生；跳过是期望
> 本来就是不提单。两者在结果上看起来一样，必须靠期望区分。

### 提单场景 (ticket scenario)
一份可重复执行的测试输入及其**人工写定**的期望：提单动作，以及新建/复用时单据应有的
project、issuetype、assignee、components、labels，或应命中的已有单。期望不得由
业务代码自身推算。

### 提错单
实际动作或单据字段与场景期望不一致。最常见的是 project 或 assignee 路由错误。

### 原定指派人 (intended assignee)
测试模式下业务逻辑**本来要指派**的人。测试模式会把实际指派改写为固定测试人员，
原定指派人必须单独留存，才能校验指派是否正确。

### 测试 JIRA 项目
提单回归产生的所有单据落入的 JIRA 项目：`VELAEFF`。

### 回归运行 (regression run)
一次批量执行若干提单场景的过程，以 `regression_run_id` 唯一标识。回归运行在
**测试环境**中执行，单据全部落入测试 JIRA 项目，不打线上服务。

### 回归标记 (regression marker)
附着在**单条输入**上的 `regression_run_id` 与场景 id，随资源/记录一路传递到提单
那一步，用于给测试单打上场景标签、把结论归到对应场景。它**不承担隔离职责** ——
隔离由测试环境本身保证。

### 回归标签 (regression labels)
测试 JIRA 项目中每张回归单携带的一组 label：所属回归运行、场景、问题类别、期望
指派人、原定指派人、判定结论（通过/不通过）。用于在 JIRA 中直接筛选、识别"指派
准不准"。

### 回归汇总单
每次回归运行在测试 JIRA 项目中建的一张汇总单，记录**没有产生单据**的场景（跳过、
提不了单、超时）的期望、实际与原因码，使一轮运行的全貌都能在 JIRA 中看到。

### 跳过原因码 (skip reason)
提单动作为"跳过"时给出的具体规则名（如 `debug_remark`、`image_over_48h`）。场景
期望为跳过时必须连同原因码一起断言。

## 分析回归（vela-tools → VelaAgent AI 辅助分析链路）

### 分析场景 (analysis scenario)
一份可重复执行的分析输入及其**人工写定**的期望。输入按**入口 × 问题类型**切分
（crashlog/crash、autotest/testcase、circle/circle、jql/coverity、jql/crash、
manual）。期望包括：期望指派对象、期望垂域、是否应主动分析。初值取线上该单的最终
结论，经人工确认后固化。

> 与"提单场景"区分：提单场景断言**开不开单、单开给谁**；分析场景断言**单同步到
> VelaAgent 之后，派给谁、分析得对不对**。

### 分析回归运行 (analysis regression run)
每日在测试环境执行一遍全部分析场景的过程。结果按天留存，用于跨天比对耗时与达标率。

### 垂域 (domain)
VelaAgent 分诊（router）为一个问题判定的问题领域，如 crash / hybrid_os / ui / net /
bluetooth / media / telephony / vtf。垂域是分析的**输出**，不是场景的输入维度。

> 与**领域团队**区分：领域团队（多媒体 / 图形 / 网络 / 系统…）是按**解决人**归属的
> 人员组织维度，与垂域正交。`multica_jira_bridge` 的 system / graphic 大类、原型里的
> Audio / Display 模块也都不是垂域。

### 期望指派 (expected assignment)
分析场景中写定的两层期望：vela-tools 侧把单派给**小队还是哪个 Agent**；VelaAgent
侧分诊出的**垂域及其求解 Agent**。两层分别判定。

### 仅总结 (summarize-only)
circle 全闭环单的期望行为：同步后指派给**总结 Agent**，只产出一段话总结，不做完整
分析、不回写 Jira 分析报告；直到有人在单上 @ 它，才开始完整分析。总结 Agent 未配置
时（灰度期）不指派、不产出。

### 追问续析 (follow-up analysis)
已出结论的单上，人再次 @ Agent（质疑垂域或补证据）后，Agent 开新一轮分析并再次走到
结论的过程。

### 过程合规 (process compliance)
一次分析的流程层面是否正常：打点齐全、指派与垂域符合期望、命中了 skill / 知识卡片、
产出了带根因的最终结论。每次运行自动判定。

### 结论正确 (conclusion correctness)
分析结论本身是否正确。只在**金标准样本**上自动判定。

### 金标准样本 (gold sample)
线上已有人工反馈（有用 / 部分有用 / 无用）的单，用其反馈作为结论正确与否的依据。

### 不达标 case
过程合规或结论正确判定未通过的单次分析。不达标 case 交由 AI 结合源码做根因分析、
给出修复方案，供次日人工 review。

### 基线样本 / 探索样本 (baseline / exploratory sample)
基线样本是每个分析场景固定的一组单，每次运行都重跑，**只有它参与跨天趋势对比**。
探索样本是每次运行从线上新抽的单，用于发现新问题，不计入趋势。

### 达标线 (pass threshold)
过程合规率 ≥ 95%；金标准样本的结论正确率（反馈为有用或部分有用）≥ 70%。低于达标线
的运行在看板上高亮。

### case 超时 (case timeout)
单个 case 在一次运行中等待终态的上限：主动分析 60 分钟，仅总结 5 分钟。超时
记为不达标。

## OneTrack 打点

### 过程健康指标 (process health metric)
描述链路**运行得好不好**的指标：节点成功率、失败原因、吞吐、耗时、异常分布。只放在
OneTrack，受众是平台组。

> 与**业务结果指标**（AI 准确率、闭环率、垂域/团队统计）区分：后者依赖事后才知道的
> 状态，只放在数据库看板。同一指标只有一个口径来源，见 `docs/adr/0006-*`。

### 节点 (node)
一个可单独统计成败与耗时的打点位置，如 `crash_jira_create`、`test_mq_consume`。
平台上所有节点共用一个事件 `vt_event`，靠参数 `node` 区分，见 `docs/adr/0007-*`。

> 与 crashlog 的 `node_name`（agent 实例名）无关。

### 链路 ID (trace_id)
把同一任务（一个 CT 任务、一个 crash 资源、一次手工提单）的各节点事件串起来的标识。
**只用于串联，不承载业务结果。** 作业级、整批事件不属于任何单个任务，不带链路 ID。

### 节点结果 (result)
节点一次执行的结论，只取 success / failed / skipped（通知节点用 sent 代替 success）。
外层节点的结果必须反映下游的真实成败，下游失败不得记成成功或跳过。

## 自动化测试看板与子页

### 自动化测试看板 (task dashboard)
按任务线展示自动化测试执行情况、开关与预警状态的总入口页。CT 失败分析、用例与
覆盖度、执行记录、预警记录、预警规则、数据同步都从这里进入。
_避免_：测试看护看板

### CT 失败分析 (CT failure analysis)
CT 失败的三种排名：每日失败用例、根因、失败任务。用于定位问题，不用于实时盯盘。
_避免_：CT 失败看板

### 用例与覆盖度 (case & coverage stats)
按团队统计的用例分布和代码覆盖度。
_避免_：测试看板、测试数据看板

### 执行记录页 (execution records)
一次测试执行一行的列表，可按状态、失败原因、耗时、责任人筛选。
_避免_：测试任务汇总

### 预警记录 (alarm record)
已经发出的预警通知的留存，可以标记为已解决。失败率预警也是其中一种类型。
_避免_：预警通知（指的是同一件事）

### 预警规则 (alarm rule)
决定什么情况下产生预警的规则，可以启用或停用。它和预警阈值是两回事。
_避免_：预警设置

### 预警阈值 (task alert threshold)
在看板上针对单条任务线设置的失败率预警阈值。

### 数据同步 (sync management)
任务线执行记录同步的配置、状态、启停和手动同步。
_避免_：同步配置（只描述了其中一部分）

## 自动化测试执行记录同步（alarm 模块）

### 执行记录 (execution record)
珊瑚海一次 CT 任务的执行，对应 `vela_autotest_execution_record` 一行。记录的 id
即珊瑚海的 `ct_task_id`，因此回调与记录可以一一对应。

### 任务线 (task_key)
一条持续产生执行记录的珊瑚海任务配置，如 `admission_sim-vela_rel-5.0`。同步、
预警、看板都以任务线为单位。

### 未完成记录 (unfinished record)
状态为 `ready` 或 `running` 的执行记录。定时同步**只关心未完成记录**，已进入终态的
记录不再跟进。

> 这里的 `ready` 是珊瑚海任务状态，与 crashlog 的**就绪 (readiness)** 无关。

### 状态同步 (state sync)
定时向珊瑚海查询 `ready`、`running` 两种状态的执行记录：本地没有的入库，本地已有的
跟进到最新状态。

### 批量核查 (batch check)
本地仍是未完成记录、但在本轮状态同步里已经查不到的记录，按 id 批量向珊瑚海查询
真实状态。它补上回调没有送到的那部分。6 小时的僵尸收口仍是最终兜底。

### 珊瑚海回调 (callback)
珊瑚海在执行记录跑完后主动推送的结果。回调是执行记录**进入终态最快的渠道**。回调
到达时本地若还没有该记录（任务在两轮同步之间就已跑完），先按 id 补查再更新。

### 回调缺失 (missing callback)
批量核查发现执行记录在珊瑚海侧已经结束超过一轮同步间隔，本地却一直没有收到回调。
它说明回调链路可能出了问题，计入同步失败预警的汇总卡片，不单独通知。刚结束不久、
回调可能只是晚到的记录不算回调缺失。

### 同步失败预警 (sync failure alert)
某条任务线向珊瑚海**拉取数据失败**（接口报错、拉不到数据）而产生的预警。只针对
同步本身，**不包括测试任务执行失败**——后者由失败率预警覆盖。每轮同步的全部失败
任务线合成一张汇总卡片，发到自动化测试框架开发小组群，并留存为历史预警。

### 已处理 (handled)
研发对一条同步失败预警的确认。标记后该任务线停止通知；它下次同步成功后若再次
失败，重新开始通知。

### 手动纠偏同步 (manual full sync)
在同步配置页对单条任务线人工触发的同步。与定时的状态同步不同，它拉取该任务线
**所有状态**的最近一批执行记录，用于人工修正本地与珊瑚海不一致的状态。

## 垂域指标看板

### 垂域指标看板 (domain metrics dashboard)
按**垂域**展示 AI 分析的量、准确率、耗时、链路与工具问题、反馈的单一页面，供垂域
自己定位和优化问题。取代此前的小队运营看板与 Issue 链路看板。
_避免_：squad-telemetry 看板、issue-trace 看板（已合并）

### 准确率 (AI accuracy)
基于**用户反馈**（有用 / 部分有用 / 无用）计算的分析结论正确率。看板上只有它叫准确率。

### 反馈覆盖率 (feedback coverage)
有用户反馈的问题占全部问题的比例。它决定准确率可不可信；覆盖率过低时，垂域之间按覆盖率比较，
而不是按准确率比较。

### 自评成功率 (self-reported success rate)
Agent 自己报告"分析成功"的比例。不是准确率，只作参考。
_避免_：分析成功率、准确率

### 入口 (entry)
问题进入 AI 分析的来源：crashlog / autotest / circle / jql。机测问题即 autotest 入口
的问题。入口是筛选维度，与垂域正交。

### 同步规则 (sync rule)
研发按自己关注的 JQL 配置的定时拉单规则，拉到的问题走 jql 入口进入 AI 分析。规则上的
**产品覆盖**是研发给这批问题指定的产品，看板据此把问题归回规则。
_避免_：统计任务、同步任务、过滤器

## AI 分析周报

### AI 分析周报 (AI weekly report)
每周汇总近 7 天（滚动，按问题同步到 VelaAgent 的时间归属）AI 分析情况的报告，Markdown
与单文件 HTML 两份同内容产物，供周会呈现。

### AI 复核正确率 (AI-reviewed correctness)
由 AI 抽样复核 Agent 结论、对照 Jira 人工结论或修复记录得出的正确率。用于反馈不足时
补充参考，**不是准确率**，二者分开展示。
_避免_：准确率（准确率只指基于用户反馈的口径）

### 链路检查点 (chain checkpoint)
vela-tools → VelaAgent 执行流程上逐一核查成败的位置，共 9 个：入口建单、台账落库、
推送 VelaAgent、小队接诊、分诊出垂域、求解分析、最终结论、回写 Jira、用户反馈。
重跑是求解分析的附属指标，不单列。

### 执行问题类别 (execution issue category)
Agent 执行过程中遇到的问题按 5 类归口：**环境**（运行机、权限、依赖、超时）、
**代码下载**（源码、附件、日志、coredump 获取失败）、**工具**（命令、CLI、脚本调用失败）、
**skill**（未加载、加载错、skill 内容误导）、**MCP**（MCP 服务调用失败）。归不进的
记为「其他」。

> 与看板的**报错分层**（platform / tool / data / flow）区分：分层按责任方划分，
> 类别按问题性质划分，周报用类别。

### 已解决 (resolved)
问题对应的 Jira 单已进入解决态。VelaAgent 侧流程跑完（done）**不等于**已解决。
